# 立体ドローイングの更新・公開

依頼された修正、バージョン表記、文書、検証、公開状態を揃える。利用者の明示した範囲と公開先を優先し、このスキル自体を外部操作の許可と解釈しない。

## 1. 範囲と現在地を確認する

- 対象リポジトリのルートを確認し、`git status --short`、現在のブランチ、リモート、最近の履歴を読む。既存の未コミット変更を今回の作業と区別し、無関係な変更を含めない。
- `package.json`、`package-lock.json`、`src/config/app-version.ts`、`README.md`、`CHANGELOG.md`、`.github/workflows/pages.yml`を読む。コマンド、バージョン、テスト件数をこのスキルへ固定せず、現在のファイルから取得する。
- このプロジェクトの既存公開先はGitHub Pages、リポジトリは`rikuru-sys/SolidDrawing`、URLは`https://rikuru-sys.github.io/SolidDrawing/`。README・リモート・ワークフローで現状と照合する。古い`.openai/hosting.json`があるだけでSitesへ公開先を変更しない。不一致があり依頼から解決できない場合は公開先を確認する。
- 「準備だけ」「公開しない」は文書整備・検証までとし、プッシュ、タグ、Release作成、公開を行わない。「公開して」は依頼された公開先への反映と配信確認まで行う。通常の「修正して」だけでは公開しない。
- 中断からの再開では、ローカルとリモートのSHA、そのコミットのActions実行状態、公開サイトを照合する。成功済みのプッシュや公開を重複実行しない。

## 2. バージョンと文書を公開前に揃える

指定バージョンがあれば従う。指定がなく不具合修正の公開ならパッチ更新を基本とし、互換性を壊す変更や機能追加は変更内容に合わせて判断する。文書だけの訂正ではアプリのバージョンを自動で上げない。

| 対象 | 更新・確認内容 |
| --- | --- |
| `package.json` | アプリの`version` |
| `package-lock.json` | ルートと`packages[""]`の`version`。依存ライブラリ自身のバージョンは一括置換しない |
| `src/config/app-version.ts` | `APP_VERSION`がパッケージと一致 |
| `README.md` | 最新版、変更概要、影響する操作説明、実行方法、検証の記録、末尾の開発状況 |
| `CHANGELOG.md` | 対象バージョンの節、日付、利用者から見た変更・修正、必要な互換性や開発環境の変更 |
| 関連する`docs/` | 変更した仕様・操作・検証方法に関係する説明のみ |

- 前回の公開済み版との差分から変更を要約する。直近1コミットだけを見てリリース内容を決めない。
- 既に公開済みなのに「未公開」に残っている項目は、Git履歴で所属バージョンを確認して移す。分からない日付や所属を推測で埋めない。
- README冒頭だけでなく、古いバージョン表記、件数、機能説明が残っていないか確認する。過去の事例として正しい記述は保持する。
- テスト件数や成功結果は、対象の実行結果から記録する。テスト一覧を取得しただけでは成功と記載しない。公開前に「公開成功」と記載せず、準備中・検証済み・公開済みを区別する。

## 3. 公開環境に合わせて検証する

- バージョンと文書の更新後、ルートで`npm.cmd run check:release -- --version 対象バージョン`を実行する（Windows以外は`npm`）。`--version`を省略すると`package.json`の現在値を使用するため、番号の更新自体を忘れていないか確認したい場合は対象版を指定する。
- 自動チェックの実体はルートの`scripts/check-release.mjs`。ファイルを変更せず、パッケージ・ロックファイル・APP_VERSION・READMEの最新版表記、CHANGELOGの対象節・日付・空欄・重複を検査する。成功0、不整合1、引数誤り2で終了する。不整合は直してから再確認する。
- この検査は文章の正確さ、テスト結果、公開成功を保証しない。READMEの古い操作説明や検証件数、CHANGELOGの説明内容は引き続き差分と実測に照らして確認する。検査実装を変更した場合は`npm.cmd run test:release-check`も実行する。
- 画面や保存画像の確認を依頼されている場合は、隣の[solid-drawing-visual-check](../solid-drawing-visual-check/SKILL.md)を使う。リリース依頼だけを理由に新たな網羅的画像テストを追加せず、変更と依頼に必要な検証を選ぶ。
- `packageManager`、Nodeの要件、Actionsで実際に使うバージョンを確認する。宣言だけでCIのnpmが切り替わるとは考えない。
- Windows PowerShellでは`npm.cmd`を使用する。依存関係を更新する場合は指定されたnpmのメジャー・バージョンに合わせ、ロックファイルの整合性を確認する。npm 11で更新したロックファイルがnpm 10の`npm ci`で失敗した実例がある。
- 現行ワークフローの必須チェック（依存関係インストール、監査、ユニットテスト、E2E、型チェック、Lint、Pages用ビルド）を確認する。実行済みのチェックは対象の変更が同じなら再利用する。公開環境で行うチェックは、当該コミットの成功を完了条件に含める。
- 現行の`test:e2e`はPages用ビルドを含む。同じ成果物を再利用できる場合は、理由なくビルドやテストを繰り返さない。文書のみの変更ではリンク・記述・差分を確認し、無関係なテストを追加しない。
- GitHub Pagesの成果物は現行設定では`build:pages`が生成する`pages-dist/`。`build:sites`は別のビルドであり、Pagesの検証や配信成功の代わりにならない。
- 監査・CIの失敗は具体的なログを確認し、必要な範囲だけ修正する。検査を無効化したり、`--force`や`--legacy-peer-deps`で不整合を隠したりしない。共通プラグイン・グローバル設定の書き換えを通常のリリース修正に含めない。
- 認証情報は表示・ファイル保存・コミットしない。使える認証がなければ、その操作だけを未完了として説明する。同じ原因の再実行を繰り返さず、修正や新しい証拠があるときに再試行する。

## 4. コミット前の完了表

次の項目をそれぞれ「確認済み／該当なし（理由）／未完了」として確認する。作業中は簡潔な記録を保持し、未完了を残したまま全体完了と報告しない。

- 今回公開する変更の範囲が確定している。
- パッケージ、ロックファイル、画面表示のバージョンが一致している。
- READMEとCHANGELOGが今回の内容に対応し、必要な関連資料も更新した。
- 必要な検証が成功した、または公開側で確認するチェックが明確である。
- `git diff --check`と最終差分を確認し、秘密情報・一時ログ・生成物・無関係な変更を含まない。
- 公開先、対象ブランチ、依頼の公開範囲が一致している。

準備だけの依頼はここで終了し、変更内容・検証結果・未公開であることを報告する。

## 5. 公開と完了確認

- 公開が依頼されている場合、文書を含む対象ファイルを明示してコミットする。リモートの更新を確認し、他者の変更があれば取り込む。強制プッシュはしない。
- 検証したコミットを対象ブランチへプッシュする。現在の`main`へのプッシュはPagesワークフローを起動する。タグやGitHub Releaseは、依頼やリポジトリの規約で必要な場合だけ作成する。
- プッシュの終了結果を確認し、完全なコミットSHAを取得する。そのSHAに対応するPages実行を追跡し、検証ジョブと配信ジョブの両方の成功を確認する。別のコミットの成功を流用しない。
- 公開URLのHTTP応答に加え、参照しているJS/CSSのファイル名・ハッシュ、バージョン表示などで対象の最新版が配信されていることを確認する。HTTP 200だけで最新版と判断しない。
- 失敗・実行中・配信未確認の場合は「公開済み」と報告しない。原因、確認済みの範囲、残りの作業を伝える。再開時は手順1の照合から続ける。
- 公開後に文書の追記が必要になった場合は、依頼の範囲で追記・反映し、コミットだけの状態を「GitHub反映済み」と呼ばない。文書だけの修正とアプリの追加リリースを区別する。
- 最後に公開バージョン、URL、主な変更、検証結果、残作業の有無を簡潔に報告する。

## 動作確認用の依頼例

- 「次のパッチ版のリリース準備だけして」：バージョン・文書・検証を揃え、プッシュせず終了する。
- 「READMEと変更履歴だけ訂正して」：文書を直し、アプリのバージョンを上げず、公開依頼の有無に従う。
- 「公開の続きを実行して」：リモートとActionsを調べ、既に成功済みなら再公開せず状態を報告する。
- 「バージョンを上げて公開して」：文書を含めて準備し、対象コミットの配信確認まで完了する。
